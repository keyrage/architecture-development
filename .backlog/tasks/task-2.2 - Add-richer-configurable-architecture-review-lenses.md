### Current-code V1 contract baseline (PLAN-007)

The following is verified against `architecture_review.ts`, `_lib/schemas.ts`, `_lib/review_state.ts`, and `_lib/evidence_collection.ts` and is the compatibility contract to preserve. Durable schemas are strict Zod objects; method argument wrappers use Zod `.strip()`, so **all unknown method-input keys are stripped**, not only host-merged globals. `modelId`, `endpointFile`, `bearerToken`, and optional `repositoryRoot` are examples of stripped host/global keys. Declared keys still validate, and durable records never contain credentials.

* `ReviewStateV1` is exactly strict `ReviewStateSchema`: required `reviewId` matching `[A-Za-z0-9][A-Za-z0-9_-]{0,95}`, positive integer `epoch`, `phase` in `collecting|assessing|synthesizing|dialogue|stopped|complete`, non-empty `modelId`, unique `expectedGroups` array of 1–7 values from `Motivation|Strategy|Business|Application|Technology|Physical|Implementation & Migration`, unique non-empty `selectedSpecialists` array of the six fixed IDs, and ISO `updatedAt`; optional positive integer `publishedRevision`, `apiVersion: "v1"`, and `graphContractVersion: 2`; no other keys.
* `EvidenceChunkV1` is strict `{reviewId,epoch,sequence,modelId,publishedRevision,kind,items,itemCount,digest}`: positive identity/revision, nonnegative sequence, kind `folders|elements|relationships`, `items` array of string-keyed unknown-object records, nonnegative itemCount, and lowercase 64-hex digest. `EvidenceManifestV1` is strict `{reviewId,epoch,modelId,publishedRevision,complete:true,chunkCount,counts:{folders,elements,relationships},collectedAt,restarted}` with positive identity/revision/chunkCount, nonnegative counts, ISO collectedAt, and no other keys. Chunks are written in collection order (folders pages, elements pages, relationship pages) with sequence starting at 0; the manifest follows.
* `SpecialistAssessmentV1` is strict `{specialist,modelId,publishedRevision,findings,strengths,completedAt}`. `FindingV1` is strict `{findingId,category,title,statement,canonicalIds,citations,impact?,confidence?,scope?,effort?}`; category is `observation|interpretation|assumption|recommendation`; all text/ID arrays are non-empty as currently constrained; citations are strict `{canonicalId,path?,startLine?,endLine?}`, with a path requiring positive ordered bounds and no path forbidding bounds; each optional numeric rating is integer 1–5. `AssessmentRecordV1` (the `specialistAssessments` resource) is strict `{reviewId,epoch,modelId,publishedRevision,assessments:SpecialistAssessmentV1[],recordedAt}`.
* `RecommendationV1` is strict `{recommendationId,title,statement,sourceFindingIds,citations,impact,confidence,scope,effort,score,scoreExplanation}` with nonempty text/IDs, nonempty sourceFindingIds, current citation shape, ratings 1–5, score integer 10–50, and nonempty scoreExplanation. `SynthesisV1` (the `synthesis` resource) is strict `{reviewId,epoch,modelId,publishedRevision,sourceFindingIds, strengths,recommendations:RecommendationV1[],synthesizedAt}`; it has no discriminator, qualified keys, counts, or epistemic fields. `FollowupV1` is strict `{reviewId,epoch,sequence,recommendationId,specialist,question,response,recordedAt}` with positive sequence, fixed SpecialistId, nonempty text/ID, and ISO recordedAt. `DispositionV1` is strict `{reviewId,epoch,recommendationId,disposition,rationale,recordedAt}` with disposition `accepted|rejected|deferred|needs-investigation|undecided` and rationale 1–1000 characters.
* Exact shipped V1 method inputs are `start_review {reviewId,expectedGroups?,selectedSpecialists?,epoch?}` (defaults expected groups to Application/Technology, specialists to all six, epoch to 1); `status|collect_evidence|stop|resume {reviewId,epoch}`; `record_assessments {reviewId,epoch,assessments:SpecialistAssessmentV1[]}`; `record_synthesis {reviewId,epoch,synthesis:SynthesisV1}`; `record_followup {reviewId,epoch,sequence,recommendationId,specialist,question,response}`; and `disposition {reviewId,epoch,recommendationId,disposition,rationale}`. The `.strip()` behavior applies to each wrapper.
* Exact shipped V1 outputs are start `{dataHandles:[handle],reviewId,epoch,selectedSpecialists}`; status `{state:ReviewStateV1}`; collect `{dataHandles:[stateHandle],reviewId,epoch,revision,counts:{folders,elements,relationships},restarted}`; assessments `{dataHandles:[assessmentHandle,stateHandle],specialists:[SpecialistId]}`; synthesis `{dataHandles:[synthesisHandle,stateHandle],strengths,topTen:RecommendationV1[],recommendationCount}`; follow-up `{dataHandles:[handle],specialist}`; disposition `{dataHandles:[handle],disposition}`; stop `{dataHandles:[stateHandle],stopped:true}`; unchanged-revision resume `{dataHandles:[stateHandle],freshAssessmentRequired:false,epoch}`; moved-revision resume `{dataHandles:[stateHandle],freshAssessmentRequired:true,priorEpoch,epoch}`. `dataHandles` are host handles and are not durable schema fields.
* V1 resource specs and instance formulas are `reviewState-<reviewId>-e<epoch>-s0`, `evidenceChunk-<reviewId>-e<epoch>-s<sequence>`, `evidenceManifest-<reviewId>-e<epoch>-s0`, `specialistAssessments-<reviewId>-e<epoch>-s0`, `synthesis-<reviewId>-e<epoch>-s0`, `followup-<reviewId>-e<epoch>-s<sequence>`, and `disposition-<reviewId>-e<epoch>-s<recommendationId>`. Each call to an existing instance appends a new resource version; no prior version is rewritten. Start appends state; collect appends successful chunks, manifest, then state; assessments append the normalized assessment record then state; synthesis appends synthesis then state; follow-up/disposition append their named records; stop appends stopped state; same-revision resume appends resumed state; moved-revision resume creates the next V1 epoch state and later operations append under that epoch. V1 selection stays immutable and recommendation lookup must validate against persisted synthesis before dialogue/disposition.

### Parsed V1 normalization and version lifecycle (PLAN-007/005)

Do not retain purported raw V1 bytes: the current `readResource` seam returns only `Record<string, unknown>`, so raw-byte retention is impossible and out of scope. Instead, every read parses the exact strict V1 schema above into tagged internal `NormalizedReviewV1`, `NormalizedAssessmentV1`, `NormalizedSynthesisV1`, `NormalizedFollowupV1`, or `NormalizedDispositionV1`, preserving parsed field values and the source resource/version identity. V1 finding category normalizes `observation` to factual and all other categories to heuristic; legacy missing confidence is represented as absent and is never invented. The parser rejects unknown durable keys, invalid values, mixed V1/V2 tags, and ambiguous records. No old resource version is rewritten, reserialized, upgraded, or replaced; all V1 writes remain exact V1 shapes and names.

A V1 epoch remains V1 across state changes, stop, unchanged/moved-revision resume, assessment/synthesis, follow-up, and disposition. A V2 epoch is created only by an explicit V2 start request and writes only V2 resources; it never upgrades or rewrites a V1 epoch. Resume preserves the source epoch wire version and persisted role snapshots. These are parsed-record guarantees, not claims about unavailable bytes.

### Exact V2 records, snapshots, resources, and envelopes (PLAN-005/008)

V2 resource records carry `recordVersion: 2`; V2 method envelopes carry `schemaVersion: 2`. All objects below are strict (no unknown fields), arrays have the stated uniqueness/order rules, and V2 never parses as V1.

**Role and snapshot contracts.** `RoleSnapshotV2` is a strict discriminated union. The specialist member is `{roleKind:"specialist",roleId:SpecialistId,definitionVersion:1,snapshotDigest:string,evaluatorVersion:string,definitionSnapshot:{kind:"specialist",requiredEvidenceKeys:string[],limitations:string[],applicability:{kind:"always"}}}`. The lens member is `{roleKind:"lens",roleId:LensId,definitionVersion:1,snapshotDigest:string,evaluatorVersion:string,definitionSnapshot:{kind:"lens",requiredContextEvidenceKeys:string[],requiredEvaluatedEvidenceKeys:string[],contextTrigger:PredicateV2,concernPredicate:PredicateV2,limitations:string[]}}`. Both digest must match `sha256-[a-f0-9]{64}` and evaluatorVersion must equal `specialist/<roleId>@1` or `lens/<roleId>@1`; arrays are canonical unique sorted evidence/limitation lists. `PredicateV2` is the closed strict union `{kind:"allOf",children:PredicateV2[]}` or `{kind:"anyOf",children:PredicateV2[]}` or `{kind:"not",child:PredicateV2}` or `{kind:"present",key:string}` or `{kind:"equals",key:string,value:string|number|boolean|null}` or `{kind:"contains",key:string,value:string}` or `{kind:"countAtLeast",key:string,minimum:positive integer}`. Every key must be declared by its role snapshot and context/evaluated key sets are disjoint.

`RoleSnapshotRecordV2` is strict `{recordVersion:2,reviewId,epoch,snapshots:RoleSnapshotV2[],recordedAt}` and is stored at `roleSnapshotsV2-<reviewId>-e<epoch>-s0`, exactly one snapshot per selected role in canonical specialist-then-lens order. `ReviewStateV2` is strict `{recordVersion:2,reviewId,epoch,phase,modelId,publishedRevision?,expectedGroups,selectedSpecialists,selectedLenses,roleSnapshotResourceName,updatedAt}` where phase and expectedGroups retain V1 constraints, selected arrays may each be empty but are unique canonical subsets, their combined set is nonempty, and roleSnapshotResourceName equals the formula above. Snapshots are authoritative on resume; current registry/evaluator lookup is not consulted except to fail closed if a persisted evaluator version or digest cannot be loaded/matched.

**V2 findings, assessments, synthesis, dialogue, and disposition.** `FindingV2` is strict `{findingKey,localFindingId,roleKind,roleId,category,epistemicKind,title,statement,canonicalIds,citations,confidence,impact?,scope?,effort?,basis?,limitations?}`. `findingKey` is canonical qf2 identity, localFindingId/title/statement/IDs are nonempty strings, role fields are a valid selected role, category is the four V1 categories, epistemicKind is `factual|heuristic`, citations use the exact V1 citation shape, confidence is required integer 1–5, optional ratings are integer 1–5, and basis/limitations when present are arrays of nonempty strings. qf2 is `qf2:` plus three uppercase-hex RFC-3986 percent-encoded UTF-8 components (`roleKind`, `roleId`, `localFindingId`) separated by literal `:`; only unreserved ASCII remains unescaped. Decode then re-encode must be identical; reject local-ID duplicates per role, tuple duplicates across roles, and encoded collisions.

`AssessmentRecordV2` is strict `{recordVersion:2,reviewId,epoch,modelId,publishedRevision,assessments:RoleAssessmentV2[],recordedAt}`. A specialist `RoleAssessmentV2` is strict `{roleKind:"specialist",roleId,modelId,publishedRevision,definitionVersion:1,evaluatorVersion,snapshotDigest,applicability:"applicable",checkedEvidenceKeys:string[],missingEvidenceKeys:[],evaluatedEvidenceKeys:string[],limitations:string[],findings:FindingV2[],strengths:string[],completedAt}`. A lens member is strict `{roleKind:"lens",roleId,modelId,publishedRevision,definitionVersion:1,evaluatorVersion,snapshotDigest,applicability:"applicable"|"not-applicable"|"insufficient-evidence",applicabilityRationale:string,checkedEvidenceKeys:string[],missingEvidenceKeys:string[],evaluatedEvidenceKeys:string[],limitations:string[],findings:FindingV2[],strengths:string[],completedAt}`. All role/model/revision/snapshot echoes must match state and persisted snapshots; assessments are exactly one per selected role in canonical order. Non-applicable and insufficient lenses have empty findings and recommendations.

`EpistemicV2` is strict `{mode:"factual"|"heuristic"|"mixed",factualSourceKeys:string[],heuristicSourceKeys:string[],basisSources:Array<{qualifiedFindingKey:string,basis:string}>,limitationSources:Array<{qualifiedFindingKey:string,limitation:string}>,limitations:string[]}`. Source-key arrays are unique lexicographically sorted; basisSources are the deduplicated flattened `FindingV2.basis` entries for heuristic sources, sorted by `(qualifiedFindingKey,basis)`; limitationSources are the deduplicated flattened `FindingV2.limitations` entries sorted by `(qualifiedFindingKey,limitation)`; limitations are the sorted unique union of limitation text. `RecommendationV2` is strict `{recommendationId,title,statement,qualifiedSourceFindingKeys,citations,impact,confidence,scope,effort,score,scoreExplanation,epistemic}`. Source keys are nonempty, unique, and each resolves in the persisted assessment; recommendationId must be `r2-[0-9]{8}`; ratings/score/text/citations retain the V1 constraints; epistemic is recomputed, never trusted from caller input.

`SynthesisV2` is strict `{recordVersion:2,reviewId,epoch,modelId,publishedRevision,orderedQualifiedFindingKeys,sourceReferenceCounts:Array<{qualifiedFindingKey:string,count:positive integer}>,strengths,recommendations:RecommendationV2[],synthesizedAt}`. `orderedQualifiedFindingKeys` is exactly the canonical unique assessment finding sequence: selected role canonical order (specialists then lenses), then each assessment's finding order. `sourceReferenceCounts` is exactly the sorted lexicographic list of counts from flattening every recommendation's qualifiedSourceFindingKeys, including references in multiple recommendations; its key set must equal the assessment finding set exactly, with no omission, invention, or extra key. Each recommendation source array has no duplicate key. Candidate fingerprints are `(qualifiedSourceFindingKeys sequence,title,statement)`; duplicate fingerprints are rejected. Canonical candidates sort by `(source-key sequence,title,statement)` and receive IDs `r2-00000001`, `r2-00000002`, ... starting at one; supplied IDs must equal recomputation. Recommendation confidence is recomputed as the half-up rounded arithmetic mean of its source FindingV2 confidence values and clamped to 1–5; FindingV2 confidence is required, so no missing-confidence rule is needed. Score is recomputed from the existing V1 scoring rule and caller aggregates are not trusted. Epistemic mode is factual iff all source findings are factual, heuristic iff all are heuristic, otherwise mixed; all source/basis/limitation fields follow the stable sorts above.

`FollowupV2` is strict `{recordVersion:2,reviewId,epoch,sequence,recommendationId,roleKind,roleId,question,response,recordedAt}` with positive sequence, r2 ID, selected role union, nonempty text, and ISO time. `DispositionV2` is strict `{recordVersion:2,reviewId,epoch,recommendationId,roleKind,roleId,disposition,rationale,recordedAt}` with the r2 ID, selected role union, V1 disposition enum/rationale limit, and ISO time. Recommendation lookup reads and strictly parses `synthesisV2-<reviewId>-e<epoch>-s0`, checks the r2 ID, and checks that the requested role is selected and is one of the recommendation's source roles; this is the role-qualified dialogue boundary.

**V2 resources and instance formulas.** Use distinct specs/names so a V2 write cannot collide with V1: `reviewStateV2-<reviewId>-e<epoch>-s0`, `roleSnapshotsV2-<reviewId>-e<epoch>-s0`, `evidenceChunkV2-<reviewId>-e<epoch>-s<sequence>`, `evidenceManifestV2-<reviewId>-e<epoch>-s0`, `specialistAssessmentsV2-<reviewId>-e<epoch>-s0`, `synthesisV2-<reviewId>-e<epoch>-s0`, `followupV2-<reviewId>-e<epoch>-s<sequence>`, and `dispositionV2-<reviewId>-e<epoch>-s<recommendationId>`. V2 evidence payloads are the V1 evidence fields plus `recordVersion:2`; all writes append versions and preserve prior records.

**V2 method envelopes.** `start_review` input is strict `{schemaVersion:2,reviewId,expectedGroups?,selectedSpecialists?,selectedLenses?,epoch?}` with presence-sensitive defaults: neither selection field means all six specialists and no lenses; only one means that value and the other empty; both are honored; reject unknown/duplicate IDs and an empty combined selection. Its output is `{schemaVersion:2,dataHandles:[handle],reviewId,epoch,selectedSpecialists,selectedLenses,roleSnapshotResourceName}`. `record_assessments` input is `{schemaVersion:2,reviewId,epoch,assessments:RoleAssessmentV2[]}` and output is `{schemaVersion:2,dataHandles:[assessmentHandle,stateHandle],roles:Array<{roleKind,roleId}>}`. `record_synthesis` input is `{schemaVersion:2,reviewId,epoch,synthesis:SynthesisV2}` and output retains V1 result fields as `{schemaVersion:2,dataHandles:[synthesisHandle,stateHandle],strengths,topTen:RecommendationV2[],recommendationCount,orderedQualifiedFindingKeys,sourceReferenceCounts}`. `record_followup` input is `{schemaVersion:2,reviewId,epoch,sequence,recommendationId,roleKind,roleId,question,response}` and output is `{schemaVersion:2,dataHandles:[handle],roleKind,roleId}`. `disposition` input is `{schemaVersion:2,reviewId,epoch,recommendationId,roleKind,roleId,disposition,rationale}` and output is `{schemaVersion:2,dataHandles:[handle],disposition,roleKind,roleId}`. V2 status/collect/stop/resume use strict schemaVersion-2 envelopes, preserve the corresponding V1 result fields, and add the V2 role/resource identifiers; no V2 envelope is accepted on a V1 epoch. Stop and revision movement preserve the epoch's wire version.

### Applicability algorithm and truth tables (PLAN-003/010)

Applicability uses tri-state `true|false|unavailable`; reporting order is `false < unavailable < true`, but unavailable is never coerced to false. A leaf `present|equals|contains|countAtLeast` is true for known valid present/matching input, false for known valid absent/nonmatching input, and unavailable for missing, inaccessible, or malformed input. `not` maps true to false, false to true, and unavailable to unavailable. Composite truth tables are:

| operator | result |
|---|---|
| `allOf` | any child false => false; otherwise any child unavailable => unavailable; otherwise true |
| `anyOf` | any child true => true; otherwise any child unavailable => unavailable; otherwise false |
| `countAtLeast` | known collection count meeting minimum => true; known count below minimum => false; unavailable/malformed collection => unavailable |

Thus allOf has false dominance and anyOf has true dominance at the composite level. Separately, before classifying a role, validate every declared required context-trigger input. Any missing/inaccessible/malformed required trigger key makes the role `insufficient-evidence` with sorted missingEvidenceKeys, even if a composite could otherwise report false or true; this prevents a hidden unavailable leaf. With complete trigger inputs, context=false means `not-applicable`; context=true means validate every required evaluated-evidence key before evaluating concern predicates, and any unavailable/malformed required evaluated value means `insufficient-evidence`. Only complete evaluated evidence can produce `applicable`; concern predicates false then produce `applicable` with zero findings (not not-applicable). Concern true evaluates findings. Persist status, rationale, sorted checkedEvidenceKeys, sorted missingEvidenceKeys, evaluatedEvidenceKeys, and limitations. Declaration validation rejects undeclared keys, malformed trees, duplicate/overlapping key declarations, context/evaluated overlap, and any specialist trigger tree.

Exact boundary tests include: allOf(false,unavailable)=false but unavailable required input preflight=insufficient; allOf(true,unavailable)=unavailable; anyOf(true,unavailable)=true but unavailable required input preflight=insufficient; anyOf(false,unavailable)=unavailable; complete false context=not-applicable; true context plus malformed required evaluated value=insufficient; true context plus complete evaluated evidence and false concern=applicable with zero findings; and context/evaluated key overlap rejected. Every one of the eight lenses gets applicable, not-applicable, insufficient, and applicable-zero-finding fixtures, with overlap and unavailable assertions.
